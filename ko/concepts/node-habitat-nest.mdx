Symphony는 하드웨어 식별, 소프트웨어 구성, 사용자 워크로드를 분리하는 세 가지 물리적 개념을 정의합니다. 이 개념들은 인프라 관심사를 구분하여 각각을 독립적으로 판단할 수 있게 해 줍니다.

## Node

**Node**는 구체적으로 식별된 리소스를 가진 대상 물리적 컴퓨터 리소스입니다. 소프트웨어만 연결 해제, 재연결, 재시작 또는 재플래싱하는 것으로는 새로운 물리적 Node가 생기지 않습니다. 파괴, 물리적 교체, 또는 중요한 로컬 하드웨어 변경은 새로운 Node를 만듭니다. Node 인카네이션은 해당 Node가 거래 시스템, 연구 클러스터 또는 Symphony로 구축된 다른 시스템의 참여자로 버스에 연결될 때 생성되는 별도의 증거입니다.

## Habitat

**Habitat**은 사용자가 선택한 작업을 위해 Node에 제공되는 정확한 운영 체제 및 패키지 구성입니다. 기본값은 필요한 소프트웨어 표면만 포함하며, 관련 없는 패키지, 숨겨진 런타임, 컨테이너, Kubernetes, 암묵적인 가상화는 포함하지 않습니다. 범용으로 넓게 구성된 Habitat도 여전히 유효한 명시적 사용자 선택입니다.

## Nest

**Nest**는 사용자가 선택한 목적을 수행합니다. 실시간 전략 실행이 일반적인 용도일 것으로 예상되며, 하나의 전략에 여러 모듈식 코드 섹션이 포함될 수 있습니다. Symphony는 Nest의 목적을 정의하지 않으며, 이를 하나의 소스 파일, 프로세스, 알고리즘, 브로커 API 또는 데이터 인터페이스와 동일시하지도 않습니다. 전략 로직은 사용자의 영역으로 남습니다.

## 비교

| 개념 | 정의 | 변경 요인 |
| --- | --- | --- |
| **Node** | 특정 리소스를 가진 물리적 컴퓨터 | 물리적 파괴, 교체 또는 중요한 하드웨어 변경 |
| **Habitat** | Node에 적용된 정확한 OS 및 패키지 구성 | 명시적인 사용자 선택 또는 qxctl이 관리하는 구성 |
| **Nest** | Habitat에 배치된 사용자 목적의 워크로드 | 사용자의 전략 또는 기타 선택한 작업 배포 |

## 클러스터와 버스 토폴로지

여러 Node는 하나 이상의 버스를 통해 서로 연결된 경우에만 클러스터를 형성합니다. 하나의 클러스터 안에 여러 버스 패브릭이 공존할 수 있으며, Node와 클러스터 간의 관계는 물리적 Node의 식별을 바꾸지 않고 관련 버스를 식별할 수 있습니다.

NATS JetStream, ZeroMQ와 같은 버스 어댑터는 원칙이 아니라 사용자의 선택입니다. 대용량 전송, 제어, 연구, 실행 배출 트래픽이 하나의 버스를 공유할 필요는 없습니다. 토폴로지는 여러 버스를 사용하거나 선언된 경로에 대해 버스를 우회할 수 있습니다.

## TOPS와 TROG 범위

**TOPS**는 지배적인 Trade Operating System 범위입니다. **TROG**는 의도적으로 하위에 위치하는 비전역 거래 그룹 범위입니다. 역사적인 표현과 달리 TROG가 반드시 가상인 것은 아닙니다. TROG의 구별되는 특성은 그 범위와 규칙이 보편적이지 않다는 점입니다.
