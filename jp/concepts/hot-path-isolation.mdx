Symphony は管理作業を実行作業から分離し、ライブトレーディング、リサーチ、その他のパフォーマンスに敏感なパスがジッター、レイテンシー、隠れた依存から解放された状態を保ちます。qxctl とナレッジプレーンは、コールドパスまたはフリージングパスの管理です。ライブ処理もホストしている Node に対して明示的に操作することはできますが、継続的なホットパス依存になってはなりません。

## コールドパスとフリージングパスの規律

qxctl と vector エンジンは、管理用のコールドパスまたはフリージングパスのコンポーネントです。これらは次のことをしてはなりません:

- ホットまたはウォームの実行パスとインラインで実行する
- ライブワークロードとロックを共有する
- ジッターやレイテンシーを増やす同期的な依存を作る
- 隠れたウォッチャー、常駐インタープリター、要求されていないバックグラウンドのパッケージマネージャーになる
- 実行 Node 上に継続的に常駐する

このルールは、ナレッジセッションコーディネーター、vector エンジン、qxctl が管理するすべての操作に適用されます。これらはエビデンスを生成し、状態を検証し、計画を準備しますが、ライブ実行パスには参加しません。

## バスの規律

大量転送、制御、リサーチ、実行の排出データが 1 つのバスを共有する必要はありません。トポロジーは複数のバスを使用したり、宣言されたパスについてバスをバイパスしたりできます。特に、共有トラフィックがジッターを生む可能性がある場合に有効です。NATS JetStream、ZeroMQ、その他のファブリックはアダプターであり、ユーザーの選択です。qxctl にバス管理機能があるからといって、バスの経由が必須になるわけではありません。

レイテンシーとスループットの要件に合ったバストポロジーは、あなたが選択します。Symphony は、単一の共有ファブリックを強制することなくその構成をサポートします。

## Prima Parte

**Prima Parte** は承認済みの Phase 3 のコンセプトであり、現時点の実行可能ファイルではありません。重要な操作の後に qxctl によって明示的に呼び出される、オプションで非常に軽量な C++ の Node ローカル状態ウィットネスです。デーモン、リスナー、タイマー、ウォッチャー、ポーリングループ、常駐のバス接続は持ちません。

その限定された永続的な語彙には、次の 3 つの用語が含まれます:

- `current` — 現在観測されている状態
- `previous` — 重要な操作の前の状態
- `lastTransmitted` — 関連するコマンドの実行後にリモート Node が送信した状態 (受信は確認されていない)

Prima Parte は自身の Node のみを記録し、小さな Maestro になることはなく、限定された作業の後に終了します。Phase 1 の Maestro レセプターではなく、実行可能ファイルもまだ実装されていません。
