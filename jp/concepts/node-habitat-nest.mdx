Symphony は、ハードウェアのアイデンティティ、ソフトウェアの構成、ユーザーのワークロードを分離する 3 つの物理的な概念を定義します。これらの概念によってインフラストラクチャの関心事が区別され、それぞれを独立して検討できます。

## Node

**Node** は、具体的に識別されたリソースを持つ、ターゲットとなる物理コンピューターリソースです。ソフトウェアの切断、再接続、再起動、再フラッシュだけでは、新しい物理 Node は作られません。破壊、物理的な交換、またはローカルハードウェアの重要な変更によって新しい Node が作られます。Node インカネーションは、その Node がトレーディングシステム、リサーチクラスター、またはその他の Symphony で構築されたシステムの参加者としてバスに接続されたときに作成される、別個のエビデンスです。

## Habitat

**Habitat** は、あなたが選択した作業のために Node に提供される、厳密なオペレーティングシステムとパッケージの構成です。デフォルトでは必要なソフトウェアサーフェスのみで構成され、無関係なパッケージ、隠れたランタイム、コンテナ、Kubernetes、暗黙の仮想化は含みません。広範な汎用 Habitat も、明示的なユーザーの選択として有効です。

## Nest

**Nest** は、あなたが選んだ目的を果たします。ライブ戦略の実行が一般的な用途として想定され、1 つの戦略が多数のモジュール式コードセクションを含む場合もあります。Symphony は Nest の目的を定義せず、1 つのソースファイル、プロセス、アルゴリズム、ブローカー API、データインターフェースと同一視することもありません。戦略ロジックはあなたの領域です。

## 比較

| 概念 | 内容 | 変更の要因 |
| --- | --- | --- |
| **Node** | 特定のリソースを持つ物理コンピューター | 物理的な破壊、交換、またはハードウェアの重要な変更 |
| **Habitat** | Node 上の厳密な OS とパッケージの構成 | ユーザーによる明示的な選択、または qxctl が管理する構成 |
| **Nest** | Habitat に配置されるユーザー目的のワークロード | ユーザーによる戦略やその他の選択した作業のデプロイ |

## クラスターとバストポロジー

複数の Node は、1 つ以上のバスを通じて互いに接続された場合にのみクラスターを形成します。1 つのクラスター内に複数のバスファブリックが共存でき、Node とクラスターの関係は、物理 Node のアイデンティティを変えることなく該当するバスを識別できます。

NATS JetStream や ZeroMQ などのバスアダプターはユーザーが選択するものであり、ドクトリンではありません。大量転送、制御、リサーチ、実行の排出データが 1 つのバスを共有する必要はありません。トポロジーは複数のバスを使用したり、宣言されたパスについてバスをバイパスしたりできます。

## TOPS と TROG のスコープ

**TOPS** は、支配的な Trade Operating System のスコープです。**TROG** は、意図的に従属させた、グローバルではないトレーディンググループのスコープです。歴史的な表現にもかかわらず、TROG は必ずしも仮想的なものではありません。その特徴は、スコープとルールが普遍的ではないという点にあります。
