Symphony 准则界定了平台控制的内容与你控制的内容之间的边界。这些规则约束着 monorepo 中的每一项设计决策，以及与 qxctl、vector 引擎和知识契约的每一次交互。

## 用户所有权

你拥有自己的策略逻辑、Nest 用途、提供商选择、硬件选择、总线拓扑以及受支持的适配器选择。Symphony 提供精确的兼容性证据和受支持的操作，但不会把建议变成平台法则。平台会报告匹配项、不匹配项、未解决的事实及其后果。它不会对提供商进行排名、规定策略，也不会悄悄扩大你的环境。

## 热路径保护

热路径受到保护，免受管理性常驻和意外共享总线压力的影响。qxctl 和知识平面属于冷路径或冻结路径管理。它们可以显式地作用于同时承载实时工作的 Node，但绝不能成为持续的热路径依赖、隐藏的监视器、常驻解释器或未经请求的后台包管理器。你的显式架构始终拥有最高主权。

## 命令与语义分离

qxctl 负责命令语法和呈现。领域 vector 负责这些命令所暴露的操作及其含义。qxctl 路由调用由所有者定义的能力，而不会吸收其语义。

## 名称与命名空间

名称记录在其所属的作用域之下。SNV 和 SCNV 不会规定名称，根 NAMESPACES 的范围也比 SNV 更广。在某个 TOPS 或 TROG 中注册的名称遵循该作用域。在多个集群中，Node 短名称可以在不同集群中重复出现，但不能在同一集群中含糊地标识两个活动的 Node。

## 调用方类别中立

调用方被归类为人类、AI、代理、服务还是工作负载，既不会授予也不会撤销权限。受支持的授权决策依据目标主机的所有权或已授予的权限、所请求的操作和资源、预期状态以及所有者配置的安全措施。目标主机的管理员对可配置的治理拥有主权。SSIAG 可以验证并投影有效的主机权限，但不会创建更高级别的注册机构。增强的身份保证和治理联锁是与调用方无关、由所有者配置的安全措施。协议完整性要求仍然是强制性的。Symphony 不会根据调用方类型来判定外部法律或财务能力。

## 事实与证据

当前契约描述当前事实。不可变的 SCLV 和 SODV 记录保存了在其记录时间点上已知、已更改、已授权或已完成的内容。当当前契约、实现证据与最新适用记录之间存在分歧时，该分歧会作为漂移呈现以供审查。历史不会被悄悄改写以迎合现状。

## Python 准则

第一方 Symphony 源代码、生成器、schema 编写、测试和验收辅助工具不需要任何 Python 实现或解释器依赖。C++ 负责替代的编写和进程测试工具。此仓库策略不限制你自行编写的程序或你明确选择的隔离 Habitat。
