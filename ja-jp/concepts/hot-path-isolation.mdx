Symphony は管理作業を実行作業から分離し、ライブトレーディング、リサーチ、その他のパフォーマンスが重要なパスがジッター、レイテンシー、隠れた依存関係の影響を受けないようにします。qxctl とナレッジプレーンは、コールドパスまたはフリージングパスの管理機能です。ライブワークもホストしている Node に対して明示的に操作することはできますが、継続的なホットパスの依存関係になってはなりません。

## コールドパスおよびフリージングパスの規律

qxctl とベクターエンジンは、管理用のコールドパスまたはフリージングパスのコンポーネントです。次のことを行ってはなりません。

- ホットまたはウォームの実行パスとインラインで実行する
- ライブワークロードとロックを共有する
- ジッターやレイテンシーを増やす同期的な依存関係を作る
- 隠れたウォッチャー、常駐インタープリター、要求されていないバックグラウンドのパッケージマネージャーになる
- 実行用の Node に継続的に常駐する

このルールは、ナレッジセッションコーディネーター、ベクターエンジン、qxctl が管理するすべての操作に適用されます。これらはエビデンスを生成し、状態を検証し、計画を準備しますが、ライブ実行パスには参加しません。

## バスの規律

大量転送、制御、リサーチ、実行の排出データは、1 つのバスを共有する必要はありません。トポロジーでは、特に共有トラフィックがジッターを引き起こす可能性がある場合、複数のバスを使用したり、宣言されたパスでバスをバイパスしたりできます。NATS JetStream、ZeroMQ、その他のファブリックはアダプターであり、ユーザーが選択するものです。qxctl にバス管理機能があるからといって、バスの経由が必須になるわけではありません。

レイテンシーとスループットの要件に合ったバストポロジーは、あなたが選択します。Symphony は、単一の共有ファブリックを強制することなく、その構成をサポートします。

## Prima Parte

**Prima Parte** は承認済みのフェーズ 3 の概念であり、現時点の実行可能ファイルではありません。これは、重要な操作の後に qxctl によって明示的に呼び出される、オプションの非常に軽量な C++ 製の Node ローカル状態ウィットネスです。デーモン、リスナー、タイマー、ウォッチャー、ポーリングループ、常駐するバス接続は持ちません。

範囲が限定された永続的な語彙には、次の 3 つの用語が含まれます。

- `current` — 現在観測されている状態
- `previous` — 重要な操作の前の状態
- `lastTransmitted` — 関連するコマンドの実行後にリモート Node が送信した状態（受信は確認されていません）

Prima Parte は自身の Node のみを記録し、小型の Maestro になることはなく、範囲が限定された作業を終えると終了します。フェーズ 1 の Maestro レセプターではなく、実行可能ファイルはまだ実装されていません。
