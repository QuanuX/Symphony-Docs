Symphony 准则界定了平台所控制的内容与你所控制的内容之间的边界。这些规则约束着 monorepo 中的每一项设计决策，以及与 qxctl、vector 引擎和知识契约的每一次交互。

## 用户所有权

你拥有自己的策略逻辑、Nest 用途、提供商选择、硬件选择、总线拓扑以及受支持的适配器选择。Symphony 提供精确的兼容性证据和受支持的操作，但不会把建议变成平台法则。平台会报告匹配项、不匹配项、未解决的事实及其后果。它不会对提供商进行排名，不会规定策略，也不会悄悄扩大你的环境。

## 热路径保护

热路径受到保护，不受管理组件驻留和意外共享总线压力的影响。qxctl 和知识平面属于冷路径或冻结路径管理。它们可以显式地对同时承载实时工作的 Node 执行操作，但绝不能成为持续的热路径依赖、隐藏的监视器、常驻解释器或未经请求的后台包管理器。你显式定义的架构始终拥有最高决定权。

## 命令与语义分离

qxctl 拥有命令语法和呈现方式。领域 vector 拥有这些命令所暴露的操作及其含义。qxctl 路由调用所有者定义的能力，但不会吸收其语义。

## 名称与命名空间

名称记录在其所属的作用域下。SNV 和 SCNV 不决定名称，根 NAMESPACES 的范围也比 SNV 更广。在某个 TOPS 或 TROG 中注册的名称遵循该作用域。在多个集群中，同一个 Node 短名称可以在不同集群中重复出现，但不能在同一集群中模糊地标识两个活动的 Node。

## 调用方类别中立

调用方被归类为人类、AI、智能体、服务还是工作负载，既不会授予也不会撤销权限。受支持的授权决策依据的是目标主机所有权或已授予的权限、所请求的操作和资源、预期状态，以及所有者配置的安全防护措施。目标主机的管理员对可配置的治理拥有最高决定权。SSIAG 可以验证和投影有效的主机权限，但不会创建更高级别的注册权威。增强的身份保证和治理联锁是与调用方无关、由所有者配置的安全防护措施。协议完整性要求始终是强制性的。Symphony 不会根据调用方类型来判定外部的法律或财务行为能力。

## 事实与证据

当前契约描述当前的事实。不可变的 SCLV 和 SODV 记录保存了在其记录的历史时间点上已知、已变更、已授权或已完成的内容。当当前契约、实现证据与最新适用记录之间存在分歧时，该分歧会作为漂移呈现以供审查。历史不会被悄悄改写成与当前一致的样子。

## Python 准则

第一方 Symphony 源代码、生成器、schema 编写、测试和验收辅助工具均不需要任何 Python 实现或解释器依赖。C++ 负责替代的编写工具和进程测试工具。此仓库策略不限制你自己编写的程序或你显式选择的隔离 Habitat。
